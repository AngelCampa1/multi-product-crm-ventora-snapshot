# Testing

The through-line: every decision here was made to answer a specific question about correctness, not
to hit a number.

---

## 1. The shape of the suite

| Layer | Runner | Environment | Covers |
|---|---|---|---|
| Unit | Vitest | node | Worker logic, DB queries, connectors, crypto, config |
| Component | Vitest | jsdom | Admin SPA pages and components |
| End-to-end | Playwright | real Worker + real D1 | Whole flows through `wrangler dev` |
| Verifiers | tsx scripts | real D1, incl. production | Schema and trigger invariants |

Exact counts are in [METRICS.md](METRICS.md), generated by `scripts/repo-metrics.mjs`.

One caveat on those counts, because it will look like an error otherwise: the metrics script counts
test cases **as declared in source**. Vitest expands parameterized `it.each` tables at runtime, so
the number it prints when you run the suite is *higher* than the number published. Run the suites
and expect a bigger figure, not a smaller one.

---

## 2. Why two Vitest configs

`vitest.config.ts` runs in `node` and carries the coverage thresholds that gate deploys.
`admin/vitest.config.ts` runs in `jsdom` with the React plugin, a setup file, and its own path
aliases.

They are separate on purpose. Merging them would mean either running React component tests in
`node`, or letting UI files that node can't meaningfully execute dilute the backend coverage gate
until it stopped meaning anything.

**The cost, stated plainly:** two commands instead of one, and `test:admin` is not currently part of
`verify:rollout`. See §7.

## 3. The coverage philosophy

This is the section most likely to be either the strongest or the weakest thing here, depending on
whether it is stated honestly. So:

**Thresholds are 95% for lines, functions, branches, and statements, enforced on seven modules, not
on the whole codebase.**

That is a deliberate choice, and the reasoning matters more than the number. A global 95% threshold
across ~14,000 lines of application code is a number, not a signal. You reach it by writing shallow
tests for view code and CRUD handlers, and it tells you nothing about whether the parts that can
actually hurt you are correct. Worse, it creates pressure to write tests that exist to move a
percentage.

So the threshold is scoped, and the selection rule is explicit:

> A module is in scope if a bug in it causes an **authentication bypass**, a **data-isolation
> violation**, or **silent data loss**.

| Module | Why it qualifies |
|---|---|
| `src/lib/firewall.ts` | The conflict-of-interest invariant |
| `src/lib/sdr-hmac.ts` | Signature verification and constant-time comparison |
| `src/routes/sdr-ingest/index.ts` | The server-to-server gate and replay store |
| `src/db/sdr-leads.ts` | The lead write path |
| `src/routes/admin/sdr-leads.ts` | Admin access to that data |
| `src/config/sdr-product-aliases.ts` | A mis-mapped slug routes a lead to the wrong product |
| `src/widgets/feedback-button.ts` | Renders into third-party pages |

**The exclusions are just as deliberate.** `src/lib/auth.ts` and `src/lib/cache.ts` are *not*
excluded because they are unimportant: they are the most security-critical files in the repo. They
are excluded because they cannot be meaningfully unit-tested in node: they depend on
`caches.default` and Workers `crypto` globals. Mocking those would test the mock. They are exercised
instead by the Playwright suite against a real `wrangler dev`, notably
`tests/e2e/access-auth.spec.ts`.

**And the honest caveat:** everything outside those seven modules has tests, but no enforced floor.
That is a scope decision, not an accident, and it means the 95% figure should never be quoted
without its scope attached.

## 4. The real-D1 harness

`tests/helpers/real-d1.ts`: 147 lines, zero dependencies.

It uses `node:sqlite` (built into Node 22) to build an in-memory database, applies **every file in
`migrations/` in lexical order**, and exposes a thin adapter implementing exactly the D1 surface
that `src/db/*.ts` actually calls: `prepare`/`bind`/`first`/`run`/`all`, returning D1's real result
shapes including `meta.changes` and `meta.last_row_id`.

The consequences are what make it worth having:

- Tests run against **real SQL, real constraints, and real triggers**.
  `customer-products-firewall.test.ts` can assert that a firewall violation genuinely aborts,
  something a mocked D1 can never do, because a mock will cheerfully accept whatever you tell it
  to.
- Because migrations are read from disk, **a migration that doesn't parse fails the unit suite
  immediately**, rather than at deploy time.

**Limits, honestly:** SQLite is not D1. There are no D1 batch semantics, no network failures, and
different concurrency behaviour. The adapter is typed only for the surface actually used, and there
is a single `as unknown as D1Database` cast at the boundary, one deliberate, documented escape hatch
rather than casts scattered through the tests.

## 5. End-to-end against a real Worker

The Playwright `webServer` command is the evidence:

```bash
npm run build:admin && npm run db:migrate && npm run db:seed && npm run db:origins
  && wrangler dev --port 8787 --test-scheduled ...
```

Every e2e run boots a real Worker on the real runtime, against a freshly migrated and seeded D1,
with the actual built SPA, and with cron triggerable via `--test-scheduled`.

`workers: 1`, `fullyParallel: false`, `reuseExistingServer: false`, each for a reason. The suite
shares one database, so parallelism would be a correctness hazard rather than a speedup. Refusing to
reuse an existing server means a broken migration surfaces on every run instead of hiding behind a
already-warm process.

Auth is not skipped in e2e. The config supplies a stub JWKS URL alongside the dev bypass, so
`access-auth.spec.ts` exercises the **real** verification path against a controlled key.

## 6. Verifiers: a fourth test layer

Seven `verify-*.ts` scripts in `scripts/` assert invariants outside the test runner. Five of them
run against a real database and accept `--remote`, so the same assertions that pass locally can be
checked against production. The other two are deliberately different:
`verify-local-phase1-rollout.ts` builds its own isolated temporary local database and takes no
`--remote` at all, and `verify-deployed-worker.ts` asserts against the live Worker over HTTP rather
than against a database.

| Script | What it proves |
|---|---|
| `verify-firewall-triggers.ts` | Attempts a real violation and asserts the abort |
| `verify-media-triggers.ts` | Media delete guards actually fire |
| `verify-migration-state.ts` | Seeded products, origins, widget key format, live trigger count |
| `verify-migration-preflight.ts` | The schema is safe to migrate before touching it |
| `verify-local-phase1-rollout.ts` | The staged phase-1 subset applies cleanly |
| `verify-migration-phase1.ts` | Phase 1 landed as expected |
| `verify-deployed-worker.ts` | The live Worker is on the expected schema before phase 2 |

`verify-migration-state.ts` is the one that independently confirms the live trigger count of 17 that
[METRICS.md](METRICS.md) reports, two different mechanisms arriving at the same number.

## 7. The `verify:rollout` gate

Fourteen steps, one command, ordered cheapest-failure-first:

1. `lint` · 2. `typecheck` · 3. `test:coverage` · 4. phase-1 local verify · 5. `db:migrate` ·
6. `db:seed` · 7. `db:retire-products` · 8. `db:origins` · 9. `verify:migration` ·
10. `verify:firewall` · 11. `verify:media` · 12. `test:e2e` · 13. `deploy:dry-run` ·
14. `npm audit`

The design principle is that the gate **reproduces the production rollout locally before
production sees it**: a full migrate → seed → retire → origins cycle, then the verifiers against
that fresh database, then e2e, then a dry-run deploy.

**Two gaps, disclosed rather than discovered:**

- `test:admin` is **not** in this list. The admin component tests can regress without failing the
  gate.
- The gate is manual. There is no CI, so it protects the codebase exactly as much as the developer
  remembers to run it.

---

## 8. What isn't tested

No load testing. No visual regression testing: the screenshots are documentation, not assertions,
and nothing fails if the UI shifts. No mutation testing. No branch protection on `main`.

The screenshot harness has exactly one automated check: `tests/unit/screenshot-budget.test.ts` fails
the suite if `docs/screenshots/` grows past its size budget, which keeps the repository from quietly
accumulating megabytes of PNGs.
